# Information architecture

## Select the destination before writing

```text
Need to capture information
        |
Search existing knowledge
        |
Existing authoritative location? -- yes --> update it
        |
        no
        |
Would an existing document become more coherent? -- yes --> update it
        |
        no
        |
Create a new document and connect it to navigation
```

Search filenames, headings, index pages, aliases, backlinks, tags, and synonyms. Search for the entities and claims involved, not only the proposed title.

## Decide by reader task and lifecycle

Place information with material that shares its audience, task, authority, and update cadence. Separate it when at least one differs enough to make the combined document hard to use or maintain.

Good reasons for a new document include:

- a distinct reader task or decision;
- independent ownership or lifecycle;
- a point-in-time record that must preserve history;
- a focused topic that would make an existing page unreasonably broad;
- access, publication, or format requirements.

“The user asked to document it” and “the existing page is long” are not sufficient alone.

## Merge and split by coherence

Recommend a merge when several pages answer the same question for the same audience and drift independently. Recommend a split when one page serves unrelated tasks, has incompatible lifecycles, or hides important reference material inside narrative prose.

Size is a signal, not a rule. A long indexed reference may be healthy; a tiny decision record may be exactly right.

## Design for findability

- Use stable, specific names based on the domain, not temporary project jargon.
- Add new pages to an index, map, parent page, or contextual link.
- Provide links in both directions when the environment does not expose backlinks.
- Use one canonical term and aliases where the platform supports them.
- Avoid deep folder trees unless the existing system already relies on them.

## Preserve the local architecture

Do not impose a universal folder taxonomy. First infer how the collection organizes facts, decisions, policies, processes, projects, people, systems, research, plans, references, temporary notes, and history. Improve that architecture incrementally unless the user requested a redesign.
